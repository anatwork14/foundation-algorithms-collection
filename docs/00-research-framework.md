# 00 — Research Framework for Foundation Algorithms

This chapter defines a common language for studying algorithms across very different fields. The purpose is to make it possible to compare, combine, and extend algorithms without confusing problems that only look similar at the surface.

---

## 1. Start from the problem, not the algorithm

A modern engineering problem should first be expressed as a tuple:

\[
\mathcal{P}=(S,A,O,T,R,C,H)
\]

where, depending on the domain:

- \(S\): state or problem configuration;
- \(A\): available actions/decisions;
- \(O\): observations/information available to the algorithm;
- \(T\): transition or transformation mechanism;
- \(R\): reward, utility, loss, or objective;
- \(C\): constraints;
- \(H\): horizon, stopping condition, or resource budget.

Not every problem uses every field, but forcing yourself to identify them reveals which family of algorithms is appropriate.

### Example: shortest path

- state: current node;
- actions: outgoing edges;
- observation: graph and edge costs;
- transition: follow an edge;
- objective: minimize cumulative path cost;
- constraint: path connectivity;
- horizon: until destination.

### Example: LinUCB recommendation

- state/context: user, item, time, device, history features;
- actions: candidate items;
- observation before action: context features;
- transition: often ignored in the contextual-bandit model;
- reward: click, conversion, utility, or a composite metric;
- observation after action: reward of selected action only;
- objective: maximize cumulative reward / minimize regret.

### Example: reinforcement learning

The crucial difference from a contextual bandit is that the chosen action influences the next state. Therefore the algorithm must reason about delayed consequences, not just immediate reward.

## 2. Identify the information structure

The same objective can require radically different algorithms depending on what information is visible.

### Full information

After each decision, the system can evaluate all alternatives.

Example: after ranking five cached candidates, an offline simulator can score all five accurately.

### Bandit feedback

Only the outcome of the chosen action is observed.

Example: show one recommendation and only observe whether that recommendation was clicked.

### Partial observation

The system receives an observation generated by an unobserved state.

Example: a sensor measurement is noisy evidence about a vehicle's true position. This motivates Bayesian filters, HMMs, Kalman filters, and POMDPs.

### Delayed feedback

The outcome may arrive much later than the decision. Credit assignment becomes an implementation problem even if the theoretical algorithm assumes immediate reward.

### Censored or missing feedback

No observed reward does not necessarily mean zero reward. Production systems must distinguish negative outcomes from missing telemetry.

**Research implication:** information structure is often more important than the objective function when choosing the algorithm family.

---

## 3. Offline, online, and adaptive algorithms

### Offline algorithms

The complete input is known before computation begins.

Typical examples:

- sorting;
- static shortest-path computation;
- many dynamic-programming problems;
- batch optimization.

The principal concerns are time complexity, memory complexity, exactness, and numerical stability.

### Online algorithms

Inputs arrive over time and decisions may need to be made before future inputs are known.

Typical examples:

- caching;
- scheduling;
- streaming statistics;
- online matching;
- bandits.

Performance may be measured against an offline oracle using competitive ratio or regret.

### Adaptive algorithms

The algorithm changes its decision rule based on observed outcomes.

Bandits, reinforcement learning, adaptive control, Bayesian optimization, and some routing systems belong here.

An important distinction is that an online algorithm does not necessarily learn, while an adaptive algorithm updates its beliefs or policy.

---

## 4. Exactness, approximation, and uncertainty

A problem can be difficult for at least three very different reasons.

### Computational difficulty

The exact solution may be too expensive.

Responses:

- approximation algorithms;
- heuristics;
- branch-and-bound;
- randomized search;
- relaxations;
- decomposition.

### Statistical uncertainty

The system does not know the true data-generating process.

Responses:

- estimation;
- Bayesian inference;
- confidence intervals;
- online learning;
- bandits.

### Environmental uncertainty

The world changes or behaves stochastically.

Responses:

- feedback control;
- stochastic optimization;
- robust optimization;
- reinforcement learning;
- receding-horizon planning.

Do not solve statistical uncertainty with a purely computational approximation, or computational intractability with more data. They are different problems.

## 5. The main quantities used to compare algorithms

### 5.1 Time complexity

Classical asymptotic analysis asks how runtime scales with input size \(n\):

\[
O(1),\quad O(\log n),\quad O(n),\quad O(n\log n),\quad O(n^2),\quad O(2^n),\ldots
\]

But modern systems often require more dimensions:

- number of actions \(K\);
- feature dimension \(d\);
- graph size \(|V|,|E|\);
- number of samples \(N\);
- horizon \(T\);
- number of machines \(M\);
- model parameters \(P\).

A LinUCB implementation, for example, may be dominated by scoring \(K\) actions and solving or updating \(d\)-dimensional linear systems.

### 5.2 Space complexity

Memory is frequently the real constraint. Important examples include:

- dynamic-programming tables;
- graph frontiers;
- HNSW neighbor lists;
- model parameters;
- per-arm matrices in disjoint LinUCB;
- cache working sets;
- replicated logs.

### 5.3 Sample complexity

How many observations are required to achieve a desired accuracy or confidence?

This matters when data acquisition is more expensive than computation.

### 5.4 Regret

For sequential decisions, define oracle action \(a_t^*\) and chosen action \(a_t\). Cumulative regret is commonly written

\[
R_T=\sum_{t=1}^{T}\left(r_t(a_t^*)-r_t(a_t)\right).
\]

Low regret means the learner's cumulative performance approaches an appropriate oracle benchmark.

Regret is not the same as prediction error. A system can predict rewards poorly in regions it never needs to choose and still obtain low regret.

### 5.5 Approximation ratio

For optimization where exact computation is hard, an algorithm may guarantee that its solution is within a factor of optimum.

For a minimization problem, one common form is

\[
ALG(I)\leq \alpha\,OPT(I).
\]

### 5.6 Competitive ratio

Online algorithms can be compared with an omniscient offline algorithm.

### 5.7 Convergence rate

Optimization and learning algorithms may be compared by how quickly an error measure shrinks with iterations or samples.

### 5.8 Tail risk and high-probability guarantees

Expected performance can hide rare catastrophic outcomes. In safety-sensitive or expensive systems, study quantiles, worst-case behavior, constraint violations, and high-probability bounds.

## 6. Model assumptions are part of the algorithm

An algorithm is not merely its update equation. Its assumptions are part of its definition.

Examples:

- Dijkstra assumes nonnegative edge weights.
- Binary search assumes an ordered search space.
- convex optimization guarantees require convex structure.
- the classical Kalman filter assumes a linear-Gaussian state-space model for its strongest optimality statements.
- LinUCB assumes expected reward is well represented by a linear function of the supplied features, together with conditions used by its confidence analysis.
- standard stochastic-bandit theory commonly assumes some stationarity in arm reward distributions.

When an algorithm fails in production, it is often because the implementation is correct but the assumptions are wrong.

A research note should therefore contain an explicit **assumption ledger**:

| Assumption | Why needed | How to test | What happens if violated |
|---|---|---|---|
| Stationary reward mapping | permits accumulation of old evidence | rolling residual tests | stale estimates and persistent bias |
| Independent noise | simplifies confidence analysis | autocorrelation diagnostics | confidence may be too narrow |
| Linear reward model | makes LinUCB efficient | residual/nonlinearity tests | systematic underfit |
| Nonnegative graph edges | Dijkstra correctness | input validation | wrong shortest paths |

## 7. Invariants: the hidden heart of algorithm design

Many algorithms become easier to understand by identifying what remains true after every iteration.

Examples:

- binary search: if the target exists, it remains inside the maintained interval;
- Dijkstra: once a node is settled under the assumptions, its shortest distance is final;
- union-find: every element belongs to exactly one represented set;
- dynamic programming: stored entries equal solutions to defined subproblems;
- Raft: committed log entries satisfy ordering and replication safety properties;
- LinUCB: sufficient statistics summarize observations used by the linear estimator.

When implementing an algorithm, write runtime assertions or tests around its invariants whenever feasible.

---

## 8. Representation can dominate algorithm choice

The same real-world problem can become easy or hard depending on representation.

Examples:

- routing becomes graph search after places become nodes and transitions become edges;
- recommendation becomes vector retrieval after users/items become embeddings;
- scheduling becomes constraint optimization after tasks become variables and resource rules become constraints;
- code dependency analysis becomes graph traversal;
- adaptive action selection becomes contextual bandits after each candidate action receives a feature vector.

Research should therefore distinguish:

1. **representation error** — important information is absent or encoded badly;
2. **model error** — the chosen functional family is wrong;
3. **optimization error** — the model could fit, but training fails;
4. **decision error** — the prediction is acceptable but the action policy is poor.

This decomposition is extremely useful when designing hybrid systems.

---

## 9. Bias–variance–computation–exploration trade-offs

Modern algorithms often trade several resources at once.

### Bias vs variance

A simple model may be stable but systematically wrong. A flexible model may reduce bias but require more data.

### Exactness vs computation

Approximate nearest-neighbor search intentionally sacrifices some recall to improve latency and scale.

### Exploration vs exploitation

Bandit systems sacrifice some immediate expected reward to obtain information that may improve future decisions.

### Consistency vs availability/latency

Distributed systems often make explicit trade-offs about synchronization and failure behavior.

### Memory vs compute

Caching, memoization, indexes, and precomputation spend memory to save future computation.

A combination idea is promising when it improves one dimension without quietly destroying another important dimension.

## 10. A universal implementation template

For each algorithm, answer the following.

### Inputs

What are the objects, types, dimensions, ranges, and validity rules?

### State

What persistent state does the algorithm maintain?

Examples:

- priority queue;
- hash table;
- DP table;
- posterior parameters;
- replay buffer;
- covariance matrix;
- replicated log.

### Decision/update rule

Write the mathematical rule before writing production code.

### Initialization

Many algorithms are highly sensitive to initialization. Examples include optimization, clustering, bandits, and iterative numerical methods.

### Termination

Possible criteria:

- exact goal reached;
- frontier empty;
- convergence tolerance;
- budget consumed;
- fixed horizon reached;
- no improving move exists.

### Complexity

Give both asymptotic and operational costs.

### Numerical stability

Avoid explicit matrix inverses when a solve or factorization is safer. Work in log space for tiny probabilities. Normalize scales. Guard against overflow and ill-conditioned systems.

### Observability

Production implementations should expose:

- latency;
- memory;
- queue/frontier size;
- convergence diagnostics;
- confidence width or posterior uncertainty;
- reward and regret proxies;
- constraint violations;
- cache hit ratio;
- retry counts;
- data freshness.

## 11. How to evaluate adaptive algorithms without fooling yourself

Adaptive policies create a special evaluation problem: the data you observe depends on the actions your previous policy selected.

### Common mistake

Train policy B on logs created by policy A and compare B's predicted reward on all historical examples as if rewards for unchosen actions were observed. They were not.

### Safer approaches

Depending on assumptions and logging policy:

- randomized controlled online experiments;
- replay/rejection sampling from randomized logs;
- inverse propensity scoring;
- self-normalized estimators;
- doubly robust estimators;
- model-based simulation, with explicit simulator-bias warnings.

Every production bandit should log at least:

- context;
- available action set;
- selected action;
- selection probability/propensity when applicable;
- timestamp;
- reward(s) and delay;
- policy version;
- feature/model version.

Without this, future counterfactual evaluation may be impossible.

## 12. Stationarity and forgetting

Many textbook algorithms accumulate evidence forever. Real environments drift.

Strategies include:

- sliding windows;
- exponential discounting;
- change-point detection;
- periodic resets;
- hierarchical models;
- time features;
- separate short- and long-term estimators.

For example, discounted sufficient statistics for a linear online model might use

\[
A_t=\gamma A_{t-1}+x_tx_t^\top,
\qquad
b_t=\gamma b_{t-1}+r_tx_t,
\]

with \(0<\gamma\le1\).

This sacrifices some theoretical simplicity to improve adaptation in nonstationary environments.

## 13. Safety and constraints

Optimizing reward alone is frequently the wrong problem.

A better abstraction is

\[
\max_\pi \; \mathbb{E}[R(\pi)]
\]

subject to

\[
\mathbb{E}[C_j(\pi)]\leq c_j
\]

and possibly hard per-decision constraints.

Examples:

- latency budget;
- dollar cost;
- API quota;
- memory limit;
- safety rule;
- fairness constraint;
- reliability requirement.

Practical hybrid systems often need a **feasibility layer** before a learning layer:

```text
candidate actions
      ↓
hard-constraint filter
      ↓
feasible actions
      ↓
optimizer / bandit / policy
      ↓
selected action
```

This is usually safer and easier to verify than expecting a reward function to encode every hard requirement.

## 14. Composition: algorithms as modules

The most important research perspective in this collection is that algorithm families can be composed.

A useful generic architecture is:

```text
raw world state
     ↓
representation / feature learning
     ↓
retrieval / search / candidate generation
     ↓
constraint filtering
     ↓
ranking / optimization / bandit selection
     ↓
action execution
     ↓
event stream and reward attribution
     ↓
online update
     ↓
cache / memory / model store
```

Each stage can use a different foundation:

- embeddings for representation;
- HNSW for candidate retrieval;
- SAT/CSP rules for hard feasibility;
- LinUCB for adaptive selection;
- queues for execution;
- state machines for lifecycle control;
- streaming algorithms for telemetry;
- Bayesian filtering for noisy outcomes;
- replicated logs/consensus for reliable distributed state.

The research challenge is often not inventing a brand-new primitive, but finding a composition whose assumptions align.

## 15. A combination compatibility matrix

Before combining algorithms A and B, check:

| Question | Why it matters |
|---|---|
| Do they assume the same notion of state? | inconsistent state representations create hidden bugs |
| Do they operate on compatible time scales? | millisecond control and weekly learning should not share naive updates |
| Does one algorithm change the data distribution seen by the other? | adaptive selection creates feedback loops |
| Are uncertainty estimates calibrated? | downstream exploration may trust them too much |
| Is the objective aligned across layers? | local optimization can hurt global utility |
| Are constraints duplicated or contradictory? | orchestration can deadlock or oscillate |
| Are updates atomic/idempotent? | distributed retries may double-count evidence |
| Can components be evaluated independently? | otherwise regressions become difficult to diagnose |

## 16. Research protocol for a new hybrid idea

A disciplined experiment should usually proceed in this order.

### Step 1 — Formalize

Define states, actions, observations, objective, constraints, horizon, and feedback.

### Step 2 — Establish baselines

Start with the simplest algorithms that could plausibly work.

Examples:

- random;
- static heuristic;
- greedy;
- epsilon-greedy;
- linear regression + greedy action;
- UCB1;
- LinUCB.

### Step 3 — Build an oracle or upper bound

When possible, compute a hindsight optimum, simulator oracle, or relaxed bound.

### Step 4 — Isolate the proposed contribution

Use ablations. If combining HNSW candidate retrieval with LinUCB ranking, evaluate retrieval quality and decision policy separately before evaluating the full system.

### Step 5 — Stress assumptions

Test:

- drift;
- sparse rewards;
- delayed feedback;
- noisy features;
- adversarial or pathological inputs;
- cold start;
- action-set churn;
- missing telemetry;
- system failures.

### Step 6 — Measure systems cost

A statistically better policy that is ten times slower or vastly more expensive may not be better operationally.

### Step 7 — Track reproducibility

Record seeds, datasets, feature definitions, environment versions, policy versions, and hyperparameters.

## 17. A compact decision guide

Use the following as an initial map, not as a theorem.

```text
Need exact answer on known finite input?
    ├─ yes → classical algorithms / DP / graph / optimization
    └─ no
       ↓
Input too large for exact processing?
    ├─ yes → approximation / randomized / streaming / indexing
    └─ no
       ↓
Must act repeatedly while learning?
    ├─ no → supervised/statistical optimization may be enough
    └─ yes
       ↓
Does action affect future state?
    ├─ no → bandit / contextual bandit
    └─ yes → control / MDP / reinforcement learning

Need several machines to share one logical state?
    → replication + consensus + idempotent operations

Need low-latency retrieval from huge corpus?
    → index + approximate search + caching
```
